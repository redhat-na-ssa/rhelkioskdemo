# Architecting a dual-operator Motif kiosk on RHEL10 — options, not a decision

**Project:** gnome-kiosk flight-control demo
**Date:** 2026-07-10 (revised 2026-10-08: X11-under-Xwayland option A4 added, earlier X11 conclusions corrected)
**Prepared for:** internal review
**Status:** Options analysis — no direction chosen. Platform is fixed at RHEL10; everything above that (display server, window manager, toolkit, remote-access model) is open.

> **Requirement dropped (2026-07-27):** the dual-operator/multi-pointer/input-attribution requirement this document's Axis B (§4–§6) analyzes is **no longer required** — single-operator is the active target. This document is kept in full as historical record (the reasoning may be reusable if a similar requirement returns), but no further engineering work should be scoped against Axis B, the combined candidates that depend on it (Candidates 1, 2, 4, 6), or the open items in §7 that reference it. Axis A (Motif fidelity, §3) is unaffected and remains live.

> **Correction (2026-10-08) — the X11 branch was closed too broadly.** This document treated "the X.Org server is removed from RHEL 10" as closing *every* X11-based option. That conflated two different things: the standalone **X server** (genuinely gone — so real `mwm` and MPX stay ruled out) and the **X11 window-management protocol** (ICCCM/EWMH), which Mutter still implements in full as the window manager for every X11 client running under Xwayland. A direct test ([tools/x11wmtest.c](../tools/x11wmtest.c), run on RHEL 10.2 / Mutter 49.4) showed Mutter honoring exact window position, programmatic move/resize, always-on-top, iconify/restore, `DOCK` + strut work-area reservation, and `_MOTIF_WM_HINTS` — every capability this project concluded was unavailable. Those limits belong to **Wayland-native clients** (and to GTK4, which removed the corresponding APIs on every backend), not to the platform. See the new option **A4** in §3. Also as of this date: `gnome-kiosk` is no longer a target; the project direction is a locked-down standard `gnome-shell` session.

## In short

The current implementation direction — GTK4, Wayland, `gnome-kiosk`, optionally RDP for remote access — was chosen incrementally, one problem at a time. Several of those problems turned out to be platform limits, not bugs: Wayland won't give an app a toplevel's absolute position, RHEL10's Mutter silently no-ops `xdg_toplevel.set_minimized`, and GNOME's RDP backend merges every remote operator into one indistinguishable input seat (see [rdp-input-attribution.md](rdp-input-attribution.md)). An earlier draft of this document framed all three as "Wayland/Mutter limitations that don't exist on plain X11," and proposed dropping Wayland for real `mwm` + Multi-Pointer X as the clean fix. **That escape hatch does not exist on a supported RHEL 10.1 install, and it's worth being precise about why, since it rules out an entire branch of this analysis rather than just one option:**

- Red Hat's own KB states plainly that Motif is deprecated: *"The Motif widget toolkit has been deprecated in RHEL, because development in the upstream Motif community is inactive... the `motif-static` package has been removed. Red Hat recommends using the GTK toolkit as a replacement."* ([access.redhat.com/solutions/6113101](https://access.redhat.com/solutions/6113101)). Red Hat's own `mwm`-on-RHEL how-to only covers RHEL 7/8/9 and flags that same deprecation ([access.redhat.com/solutions/7020107](https://access.redhat.com/solutions/7020107)) — there is no RHEL 10 version of that guidance.
- RHEL 10's official 10.0 Release Notes, "Chapter 8. Removed features," state: *"The X.Org server... was previously deprecated and is removed from RHEL 10."* ([docs.redhat.com — 10.0 Release Notes, Removed features](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/10.0_release_notes/removed-features)). What's left, Xwayland, is documented as an X11-application compatibility layer hosted *inside* a Wayland compositor session (RHEL 10 GNOME desktop administration docs), not a standalone X server you can run an independent window manager on top of.

Put together: there is no supported RHEL 10.1 configuration that runs real `mwm` as the session's window manager, and no standalone Xorg left to host Multi-Pointer X either. That closes off the "just leave Wayland behind" branch entirely — see §3 and §4 for what that means concretely for each axis, and §6 for the ruled-out list this adds to. It does **not** mean the Motif-fidelity and dual-operator problems are unsolvable on RHEL 10 — it means the realistic options are narrower than the first draft assumed, and worth stating that way rather than chasing a path that isn't actually installable.

**Correction (2026-10-08):** the paragraph above is right about `mwm` and MPX, but wrong to call the whole "leave Wayland behind" branch closed. Xwayland is not "a standalone X server you can run an independent window manager on" — but it doesn't need to be: Mutter *is* a complete X11 window manager for Xwayland clients, and honors the same ICCCM/EWMH requests a Motif-era application relies on. An application that runs as an X11 client (GTK3 forced onto its X11 backend, or raw Xlib/Xt) gets exact positioning, keep-above, iconify and struts that a Wayland-native client cannot. Verified on-box — see §3 A4.

This document treats the problem as two mostly-independent axes — how Motif-authentic the window manager and widgets need to be, and how two simultaneous operators share one desktop and get attributed input — lays out real options for each, and then combines them into a few full candidate architectures. It calls out plainly which options are already ruled out (by testing you've done, or by what Red Hat documents as available), and which are open questions that need a verification spike before anyone commits engineering time.

## §1 — Requirements, restated

1. Pretend flight-control demo. No real data; the point is proving out window management, not building a working ATC system.
2. **Motif look *and* feel** — not reskinned decorations. How windows are moved, resized, minimized, and how their menus/buttons are activated should match 1990s Motif (`mwm`) behavior, not modern GNOME/Mutter interaction conventions wearing a Motif theme.
3. Two concurrent operators view *the same desktop image* and the application must know which operator generated any given mouse/keyboard event. Two topology variants were named as candidates, not requirements — either is acceptable:
   - **3a.** Both operators at one workstation, sharing a monitor (or monitors), each with their own keyboard/mouse.
   - **3b.** Two monitors displaying an *identical* image — including live window moves/resizes — each fed by a separate keyboard/mouse.
4. Some windows are restricted to one operator only — visible (per §3) but not interactive — to the other.
5. Target platform: **RHEL 10.1 Workstation.** Everything else (display server, WM, toolkit, remote-access stack) is open for reconsideration.

## §2 — Two mostly-independent axes

Requirement 2 (Motif fidelity) is a window-manager/toolkit decision. Requirements 3–4 (shared desktop + per-operator attribution + per-window lock) are a display-server/session-topology decision. Almost any answer to one composes with almost any answer to the other — so they're evaluated separately in §3–§4, then recombined into full candidates in §5.

**Read on this axis:** requirement 2's "not just decoration" clause can't be met by installing an authentic Motif window manager or toolkit on RHEL 10 — that path is closed at the OS level, not just untested. The realistic way to close as much of the gap as RHEL 10 allows is A2: keep GTK4 (which is, per Red Hat's own guidance, the intended Motif successor), and put deliberate engineering effort into widget-level interaction fidelity rather than CSS alone. The WM-level half of "how window actions are activated" (move/resize/lower/minimize gestures, the window-operations menu itself) stays Mutter-native on RHEL 10 regardless of toolkit choice — worth naming as a hard ceiling on how far "feel," not just "look," can go on this platform, rather than something more engineering effort would close.

> **Revised 2026-10-08:** the "keep GTK4" part of this reading no longer holds by default — see A4 below. The ceiling itself still stands: Mutter remains the window manager under every option, so move/resize/window-menu gestures stay Mutter's. What changed is how much *control* the application has over Mutter's window management, not who the window manager is.

### A4 (added 2026-10-08) — X11 client under Xwayland, managed by Mutter

**What it is.** The application runs as an X11 client instead of a Wayland-native one. Xwayland hosts it inside the normal GNOME Wayland session, and Mutter manages its windows through Mutter's own X11 window-manager code (ICCCM/EWMH) — the same protocol traffic a real Motif/Xt application generates. No standalone Xorg, no third-party window manager, no unsupported packages: `xorg-x11-server-Xwayland`, `libX11` and `gtk3` all ship in RHEL 10 and are installed by default with the GNOME desktop.

**Why this works when the GTK4 path didn't.** Every window-management wall this project hit was a gap in the **Wayland client protocol** (`xdg_toplevel` has no request to set or read absolute position, no keep-above, no strut; RHEL10's Mutter 49.4 additionally ignores `xdg_toplevel.set_minimized`). The X11 protocol has all of these, and Mutter's X11 window-manager implementation still honors them. Two different code paths inside the same compositor — the limits were never Mutter-wide.

**Verified on-box, 2026-10-08.** [tools/x11wmtest.c](../tools/x11wmtest.c) (raw Xlib; build with `gcc -O2 -Wall -o x11wmtest x11wmtest.c -lX11`) was run on `rhel10-atop` (RHEL 10.2, `gnome-shell`/`mutter` 49.4, `xorg-x11-server-Xwayland` 24.1.9) inside the autologin `gnome-shell` session, under both `NorthWestGravity` (Xt/Motif default) and `StaticGravity`. Each check reads back what the window manager actually did from the X server, not just whether the request was accepted. Result: **0 failures in both modes.**

| Test | What was requested | Result |
|---|---|---|
| T1 | Initial placement at exact x,y via `USPosition`/`PPosition` size hints | Exact (200,200 requested and got; 37 px title bar above client area) |
| T2 | `XMoveResizeWindow` after the window is mapped | Exact position and size |
| T3 | `_NET_WM_STATE_ABOVE` | Stays above a peer window even after the peer is activated; verified in `_NET_CLIENT_LIST_STACKING`, with a control run confirming normal restacking without the flag |
| T4 | `XIconifyWindow`, then restore | `WM_STATE` Iconic → Normal, position preserved — on the same Mutter 49.4 that ignores the Wayland minimize request |
| T5 | `_NET_WM_WINDOW_TYPE_DOCK` + `_NET_WM_STRUT_PARTIAL` (60 px bottom edge) | Dock placed exactly; `_NET_WORKAREA` shrank from 1280×800 to 1280×740 — real work-area reservation |
| T6 | `_MOTIF_WM_HINTS` with decorations off | Frame extents 0/0/0/0, exact position |

**GTK3 vs GTK4 — why the toolkit choice decides whether this option is easy.** Both toolkits can run on Xwayland (`GDK_BACKEND=x11`, or `gdk_set_allowed_backends("x11")` before initialising GTK). Both default to Wayland inside a GNOME Wayland session, where none of the calls below work — so the backend must be forced either way. The difference is what's left in the API once you're on X11:

| Capability needed | GTK3, X11 backend | GTK4, X11 backend |
|---|---|---|
| Set absolute position | `gtk_window_move()` | Removed from the API on all backends — raw Xlib on `gdk_x11_surface_get_xid()` |
| Read absolute position (SAVE) | `gtk_window_get_position()` | Removed — Xlib |
| Always on top | `gtk_window_set_keep_above()` | Removed — Xlib (`_NET_WM_STATE_ABOVE`) |
| Window type (`DOCK`, `DESKTOP`) | `gtk_window_set_type_hint()` | Removed — Xlib |
| Sticky / all workspaces | `gtk_window_stick()` | Removed — Xlib |
| Minimize / restore | `gtk_window_iconify()` / `gtk_window_deiconify()` | `gtk_window_minimize()` (maps to `XIconifyWindow` on X11) |
| Reserve a screen edge (strut) | No GTK API — one `XChangeProperty` on `gdk_x11_window_get_xid()` | Same — Xlib |
| Undecorated window | `gtk_window_set_decorated(FALSE)` | Same |

GTK4 removed the positioning/stacking API deliberately, for portability to Wayland, so choosing GTK4 forfeits the easy version of this option even on X11. Its X11 backend has also been deprecated upstream, with removal planned for GTK 5. GTK3 is in maintenance mode upstream, but ships in RHEL 10 (`gtk3` 3.24.43 on the 10.2 VM) and is supported for RHEL 10's lifecycle.

**What A4 would have avoided, and what it wouldn't**, mapped against the problems documented in CLAUDE.md:

- *Would not have surfaced:* SAVE/LOAD unable to restore position; the always-on-top menu bar needing a Shell extension; minimize ignored on RHEL10's Mutter 49.4; the menu bar not reserving work area for the other windows; the D-Bus layer between app and extension (`SetStates`, `ConfigureKioskChrome`, `SetWindowMinimized`) and the startup race where the extension acted before windows were mapped.
- *Would still have surfaced:* `gnome-shell` session-level problems (the startup "curtain" actor swallowing clicks, the GDM readiness race, overview/top-panel suppression) — these are session issues independent of toolkit, so a small lockdown extension is still needed, just without window control; content-driven minimum-size floors and `resizable=FALSE` pinning the size (X11 size hints carry the same min/max semantics); everything on Axis B (input attribution — Xwayland relays the one input stream Mutter already merged).
- *Untested:* `DESKTOP` type for the radar background on X11 (expected to work — EWMH defines it); whether Wayland's "negotiate back to natural size" behavior seen on the menu bar also occurs on X11.

## §4 — Axis B: dual-operator shared desktop + attribution + lock

**Two words are doing a lot of work in this section — worth being precise before the options:**
- **"Same seat"** — one Mutter session, one `wl_seat`, multiple viewers/devices pointed at it. Input from all of them arrives indistinguishable, as if from one device. This is B0, and it's proven broken (§6).
- **"Different seats, kept in sync"** — two completely independent Mutter sessions (different seat, different D-Bus, different process). No seat-merging problem for input — each session only ever sees its own operator — but *nothing* about the two sessions is actually shared; a data channel has to push state between them to make them look alike. This is B2/B4/B5 below.

**The second category has its own wall, independent of input attribution entirely: live window position cannot be synced between two independent sessions via ordinary client APIs.** Both sides of that sync would need it — the source session would need to *read* where Mutter placed its own window on screen, and the target session would need to *set* its window to that position — and GTK4/Wayland's client-facing API provides neither (`session_base_decision.md`, from this project's own earlier investigation: *"GTK4/Wayland gives apps no way to read/set toplevel x/y"*). That's not a risk that a carefully-built sync layer could mitigate — it's the same category of hard wall as B1 being ruled out, just discovered from a different angle. B2/B4/B5 can keep two sessions' *content*, *window sizes*, and *initial/cascade layout* identical; none of them can mirror an operator dragging a window to a new spot.

*Correction (2026-10-08):* this wall applies to **Wayland-native** clients only. An X11 client under Xwayland can both read and set its own absolute position (§3 A4, tests T1/T2), so the position-sync half of B2/B4/B5 is not blocked for an A4 application. Axis B as a whole remains dropped (see top of document); recorded so the reasoning isn't reused unqualified.

**The one real way around that wall:** a GNOME Shell (not `gnome-kiosk`) extension, running in-process with the compositor, can read/set window position through Mutter's internal `Meta.Window` API (`get_frame_rect()` / `move_resize_frame()`) — a genuine, documented, absolute-coordinate API, just not one exposed to ordinary Wayland clients. Getting two sessions to mirror live drags would mean a matching custom extension on *both* ends, each pushing local position deltas to the other over a small IPC channel and applying incoming ones (with real care against feedback loops — a programmatic move re-triggering an outgoing event back to itself). This is real, not hand-waving, but it means finally resolving the still-open `gnome-kiosk` vs. full-`gnome-shell` question from `session_base_decision.md` — in favor of `gnome-shell`, on *both* synced sessions — plus building and maintaining two symmetric extensions. Flagging it here as the honest "yes, if" answer, not silently ruling it out, but it's a large, specific commitment rather than a small sync layer. The *deployment* half of this is confirmed low-risk regardless: the RHEL 10 admin guide (Chapter 16, "Enabling and enforcing GNOME Shell extensions") documents installing and system-wide-enabling custom extensions as an ordinary, current, supported admin task (`/usr/share/gnome-shell/extensions/`, `enabled-extensions` in dconf, the `gnome-extensions` CLI) — what remains custom and unverified is only the extension's own code (the `Meta.Window` position sync logic itself), not how to ship it.

**A narrower, already-packaged alternative worth naming, though it doesn't fit this project's shape without more design work:** the RHEL 10 admin guide also documents `waypipe` (Chapter 2, "Remotely accessing a graphical application") — a real, RHEL-packaged tool that forwards an individual Wayland application's protocol traffic over SSH, rendering that app's windows natively in the *client's own* local compositor, rather than mirroring a remote screen. It's a genuinely different remoting shape (per-application, not per-desktop) and each `waypipe ssh <server> <app>` invocation launches its own fresh remote process, so it doesn't natively give two operators a shared live view of one running app instance without further design work — flagging it as a real, documented primitive worth knowing about, not a ready-made fifth candidate.

**Given that cost, the options below split into two families:** B2/B4/B5 sync separate sessions (content and layout, not live position, unless the Shell-extension escalation above is taken), while B3/B6 keep one literal shared session (so "including live moves" is automatically, perfectly true — there's nothing to sync) and instead intercept input for attribution *before* Mutter's single seat merges it.

### B0 — RDP shared session (`gnome-remote-desktop`, `mirror-primary`) — *the path already tested*

Full writeup in [rdp-input-attribution.md](rdp-input-attribution.md); summarized here for completeness. One GNOME session, RDP mirrors it to however many clients connect. **Confirmed by direct instrumentation, using the exact `GdkSeat`/`GdkDevice` APIs (`gdk_event_get_seat()`/`gdk_event_get_device()`) that a GTK4 app would use to differentiate input sources:** every remote operator's input collapses into one indistinguishable seat before the app ever sees it — the two sessions logged the literal same `GdkSeat` and `GdkDevice` object, not merely the same-looking device name. Those APIs are real and would work fine if more than one seat existed to query; `mirror-primary` mode never creates one, so there's nothing for them to differentiate here, no matter how the app's code is written. Note also (confirmed against actual `grdctl --help` output on the project's own RHEL10 VM): `grdctl rdp enable-view-only`/`disable-view-only` is real, but it's a single global toggle for the whole RDP backend/scope, with no per-connection argument — the same one "Remote Control" checkbox already documented in the GUI path, just exposed as a CLI flag. It can make an entire shared session view-only for every viewer, but it cannot make it view-only for one viewer and controllable for another at the same time, so it doesn't close the attribution/lock gap either. — this is Wayland's seat model and Mutter's RDP input injection working as designed, not a bug, and it holds regardless of port/credential/process topology in front of it. Two remediations exist (an RDP proxy with a custom plugin, or isolated per-role headless sessions with a sync layer) — both real engineering builds, not configuration. Covers topology **3b conceptually** (two remote viewers) but does not, on its own, satisfy requirement 3's attribution clause or requirement 4's lock — those need one of B0's own remediations layered on top, or one of B1–B3 below instead.

### B1 (ruled out) — X11 Multi-Pointer X (MPX), one shared X session

X.Org has supported multiple independent master pointer/keyboard device pairs on **one X server** since 2009 (`xinput create-master`), each with its own cursor and its own device identity visible to XInput2-aware clients — genuinely the cleanest possible fix for co-located attribution, in the abstract. It doesn't apply here: MPX is a feature of a standalone Xorg server with direct hardware device access, and RHEL 10 doesn't have one (§"In short" — Xorg is officially removed, Xwayland is a compatibility shim under Wayland, not a device-driving server of its own). There's no supported way to `xinput create-master` anything on RHEL 10, and no reason to expect Xwayland to expose distinct master devices for physical USB peripherals even experimentally, since its whole role is relaying the *one* input stream the hosting Wayland compositor already merged. Recorded here so a future session doesn't re-propose it without knowing why it was dropped — the fix belongs on whatever platform still ships a real Xorg, not RHEL 10.

### B2 — Isolated sessions via GDM "remote login" mode (kept in sync)

**This is not the same mechanism as B0, and it matters why.** The RHEL 10 admin guide (*Administering RHEL by using the GNOME desktop environment*, Chapter 1) names these as two distinct, deliberately separate features right in its own introduction: *"Desktop sharing — Allows remote clients to connect to the desktop session of the Linux user that is currently logged in on the server"* (B0 — what was tested and found broken) versus *"Remote login — Allows remote clients to open the GNOME login screen, where they can login as a Linux user with the correct credentials"* (B2). §1.5 of that same chapter, *"Connecting to a remote desktop session on a headless server for multiple users,"* is the full current RHEL 10 procedure for B2 — confirmed current, not just present in older RHEL 9 docs as first found. Verbatim from that section: *"Integrate GNOME Remote Desktop with the GNOME Display Manager (GDM) to provide remote login functionality for multiple users by using the Remote Desktop Protocol (RDP). Remote users authenticate by using a system-wide password, which grants access to the graphical login screen. Then they log in with their individual credentials, enabling remote access to the desktop environment."* The procedure: `sudo grdctl --system rdp set-tls-key/-cert/set-credentials/enable` (one shared gate credential, set once) + `systemctl enable --now gdm` + `systemctl enable --now gnome-remote-desktop.service` — after which each remote connection hits the real GDM login screen and authenticates as its own Linux account, exactly the remote equivalent of GDM's ordinary physical multi-user login screen (the same mechanism that's supported simultaneous logged-in users, via "switch user," for as long as GDM has existed) — not a second viewer merged into an existing seat. That's a different failure domain than B0's mirror-mode bug, not the same one under another name.

The same "each seat/session locally instead of remotely" idea also works with `systemd-logind` local multi-seat (see B5) instead of RDP as the transport.

### B3 — RDP proxy with a custom plugin (one shared session — the only remote option immune to the position-sync wall)

Covered fully in [rdp-input-attribution.md](rdp-input-attribution.md) §3 Path A. `freerdp-proxy` terminates each operator's RDP connection with distinct credentials and hands a custom C plugin real per-connection identity before forwarding into the *one* shared session — attribution enforced at the network edge, one literal shared framebuffer preserved. Because it's one session, "including live moves" needs no syncing at all — it's the same pixels, always. Crucially, the lock mechanism doesn't need absolute window position either: the app already knows which of its own windows a given input event landed on (GDK dispatches events per-surface regardless of where Mutter placed that surface on screen) — the plugin just needs to tag each forwarded event with which connection sent it, relayed to the app over a side-channel IPC and correlated by timestamp/sequence, and the app decides whether to honor it based on "which window, which role" — no screen coordinates change hands anywhere in that scheme. Given the position-sync wall above, this now looks like the strongest remote candidate for literally satisfying requirement 3b, at the cost this doc already named: custom protocol-plugin code, against an API surface not yet explored beyond the binary's existence.

### B4 — TigerVNC, one dedicated server process per user (remote, different mechanism than anything tried so far)

RHEL's own docs describe a second, older, and architecturally simpler pattern for concurrent multi-user remote access: `tigervnc-server`, configured via `/etc/tigervnc/vncserver.users`, which starts one independent VNC server process per account, each bound to its own display number and TCP port (Red Hat's own example starts the first user at display `:2`/port 5902). Each server spawns that user's own GNOME session on login. This is a genuinely different mechanism from everything else in this section — there is no shared daemon or shared seat to reason about at all, because there's one fully independent server process per user from the start. It's also categorically different from what this project already tried and ruled out: the earlier VNC work fanned two ports into **one shared** `gnome-remote-desktop` backend (which hung on the second connection); this is **N independent backends**, each already scoped to one user. Needs confirming this chapter/mechanism is still present in RHEL 10's reorganized GNOME documentation (found so far via RHEL 9's doc structure) before relying on it.

### B5 — Local hardware multi-seat (`systemd-logind`, no remote-desktop protocol at all)

**This is not one shared desktop, and shouldn't be read as one.** If co-located is acceptable for the near term, this sidesteps the entire RDP/VNC question category — but by giving each operator their *own*, fully independent local session (two physically separate keyboard/mouse/monitor sets, each tagged to a distinct seat via `udev`'s `ID_SEAT` property, each running its own independent GDM-launched session) — not one literal shared image with two attributable inputs. No network transport, no RDP daemon, no VNC server, nothing to have a concurrency question about. This is the same "isolated sessions + sync layer" shape as B2/B4, just with hardware as the isolation boundary instead of a remote-access protocol — which means it inherits the **same position-sync wall**: two independent seats can be given matching content, size, and starting layout, but an operator dragging a window on one monitor will not move anything on the other. **The option that would have given a genuinely single shared local desktop with distinguishable multi-device input was B1 (MPX) — ruled out.** There is no remaining option on RHEL 10 that combines one true shared desktop with locally-attributable multi-device input.

**Sourcing caveat, treat as a real gap, not a formality:** the only documentation found describing GDM/`logind` multi-seat as a working desktop feature is RHEL 7's *Desktop Migration and Administration Guide* — RHEL 7 is EOL, and this project has already found RHEL 9→10 drop legacy desktop-Linux features with no forward equivalent (standalone Xorg, Motif). The full current RHEL 10 admin guide (*Administering RHEL by using the GNOME desktop environment* — the same one that documents remote desktop, tablets, kiosk mode, and Shell extensions in detail) was read cover to cover for this reset and contains **no mention of multi-seat, `ID_SEAT`, or `loginctl` seat management anywhere in its 16 chapters**. That's a real absence in a guide that otherwise covers adjacent niche desktop-admin territory, not proof of removal by itself — the underlying `systemd-logind` primitive certainly still ships (it's core systemd, its man pages exist on any RHEL 10 box), but whether GDM still spawns a full second graphical greeter/session for a second seat the way the RHEL 7 guide describes is **genuinely untested for RHEL 10**, not "probably still works." Don't cite the RHEL 7 chapter as if it implies RHEL 10 currency — a direct `loginctl` / physical second-seat test on the actual box is required before this is anything more than an untested hypothesis.

### B6 (ruled out) — Local input-interception daemon, one shared session

**Retracted — this has the same root flaw as B0, not a way around it.** The idea was: a privileged helper grabs both physical keyboard/mouse pairs at the `evdev` level (`EVIOCGRAB`), tags each event by originating device, and re-injects into the *one* shared Mutter session through the same portal/D-Bus mechanism `gnome-remote-desktop` uses for its own virtual input, with identity relayed to the app over a side-channel and matched to the resulting GDK event by timestamp. The flaw: re-injecting through that same synthetic-input path hits the identical choke point already proven (§ B0) to discard identity before any client code sees the event — the interceptor knows who sent an event, but that knowledge doesn't survive the trip through Mutter, for the same reason it doesn't survive RDP injection. What's left is matching an out-of-band "an event is coming" message to the actual GDK event by *timing* — a heuristic, not a fact, and not something a hard per-window lock (requirement 4) should be built on. Tellingly, the demo application could do this exact correlation trick itself — read raw `evdev` in parallel with normal GDK dispatch, no privileged daemon needed — which is simpler than the original idea, but changes nothing about the reliability problem; it's the same heuristic with one less layer. **This is a compositor/protocol-layer limitation, not an app-layer one**: `GdkSeat`/`GdkDevice` correctly report whatever Mutter gives them, and Mutter (following Wayland's `wl_seat` design) never gives more than one seat's worth of identity to any client, however the client's code is written. A real fix would mean Mutter or the Wayland protocol itself preserving and exposing per-source identity to clients — genuine compositor/protocol-level engineering on someone else's release cycle, not something fixable from the app side.

**A coarser variant of the same idea does work, but doesn't satisfy requirement 4 as worded.** A local interceptor (or B3's RDP proxy) can decide, per physical device or per connection, whether to forward *any* of that source's input at all — a yes/no gate made before Mutter ever sees the event, needing no identity recovery afterward. That reliably gives "this whole session/device is read-only, that one has full control" on one genuinely shared image. It does not give per-window locking with some windows open to both roles and others restricted — which is what requirement 4 and CLAUDE.md actually specify — since that needs exactly the unreliable event-to-window-to-identity correlation described above. Worth keeping as a fallback if the requirement can be relaxed from "specific windows locked" to "one role is read-only across the whole session," but it is a relaxation, not a fix for the requirement as stated.

## §5 — Combined candidate architectures

Which candidates are even in play depends on how literally requirement 3b's "including live window moves/resizes" is meant — see the split at the end of §4's side-by-side table. Both branches are laid out here rather than picking one.

**If live-drag mirroring can be relaxed** (each operator can rearrange their own view independently after a shared starting layout):

- **Candidate 1 (co-located) — A2 + B5.** Widget-level Motif interaction work (§3) running under two local `systemd-logind` seats (separate keyboard/mouse/monitor per operator, one workstation), content/layout kept in sync by the sync layer already scoped in [rdp-input-attribution.md](rdp-input-attribution.md) §6. No remote-desktop protocol in the loop, so no RDP/VNC concurrency dependency. Needs B5's RHEL-10 confirmation (§7).
- **Candidate 2 (remote) — A2 + B2 (or B4).** Same interaction work, running under GDM's RDP remote-login mode or TigerVNC's one-server-per-user pattern. Pick B2 vs B4 based on which is confirmed for RHEL 10 first (§7).
- **Candidate 3 (minimal-change baseline) — A1 + B2/B4/B5.** Skip the widget-level interaction work, keep Motif as a CSS theme only, as today. Least new engineering; reasonable first milestone with Candidate 1/2's interaction work layered on afterward.

**If live-drag mirroring is a hard requirement** (this is what "including live moves" in the original requirement literally says, and what prompted this correction) — **this branch is weaker than the first draft presented it, and that's worth stating plainly:**

- **Candidate 4 (remote) — A1/A2 + B3.** The RDP proxy plugin is the only remote option targeting a literal shared image with attribution — but its fine-grained per-window lock (requirement 4 as CLAUDE.md actually words it) rests on the same unproven event-to-identity correlation mechanism ruled out for B6 below, not just "custom protocol code" as a cost. A coarser variant (whole-connection read-only vs. full-control, no per-window distinction) is reliably buildable; the fine-grained version isn't confirmed buildable at all yet.
- ~~Candidate 5 (co-located) — A1/A2 + B6~~ **Removed.** B6 is retracted (§4) — it shares B0's root flaw, not a way around it.
- **Candidate 6 (either topology, heaviest) — A1/A2 + B2/B4/B5 + dual custom GNOME Shell extensions.** Keep isolated sessions but close the position-sync wall directly via Mutter's in-process `Meta.Window` API on both ends, per §4. Requires resolving the standing `gnome-kiosk`-vs-`gnome-shell` decision in favor of `gnome-shell` first, and committing to building/maintaining two symmetric extensions with feedback-loop protection. The most expensive candidate in this document, but currently the **only** one with a confirmed-real mechanism (not an unproven correlation trick) for satisfying the literal requirement while keeping isolated sessions.

**Net effect on this whole branch:** with B6 gone and B3's fine-grained lock unproven, there is currently no confirmed way to get both a literal single shared image *and* reliable per-window attribution/lock, for either topology. Candidate 6 is the only path in this document with a real (if expensive) mechanism behind it; Candidate 4 remains worth pursuing only for its coarse variant unless the correlation problem gets solved.

## §6 — Ruled out, and why

**By testing already done on the project VMs:**
- **RDP shared session with no remediation (B0 alone), including the specific idea that GTK4's `GdkSeat`/`GdkDevice` APIs could differentiate sessions in this mode.** Confirmed by direct instrumentation — see [rdp-input-attribution.md](rdp-input-attribution.md) §2. Every remote operator's input collapses to the literal same seat and device object regardless of ports, credentials, or listener processes; the APIs are real, but there's only ever one seat to query in `mirror-primary` mode.
- **Two RDP/VNC ports fanned into one `gnome-remote-desktop` backend for concurrent viewing.** Separately confirmed broken for an unrelated reason: GNOME's remote-desktop backend doesn't service a second concurrent viewer at all — the second connection hangs, it never gets to the attribution question.

**By what Red Hat documents as available on RHEL 10 (this reset's finding, not yet independently tested on-box — see §7):**
- **Real `mwm` or genuine Xm/Motif widgets as the session's window manager/toolkit.** Motif is deprecated as of RHEL 9 per Red Hat's own KB, with no RHEL 10 continuation of their `mwm` how-to, and RHEL 10 has no standalone Xorg left to host `mwm` on even as a non-default option. Sourcing in §"In short."
- **Multi-Pointer X (MPX) for local dual-operator attribution.** Depends on the same missing standalone Xorg server; Xwayland doesn't provide equivalent multi-master-device support, since it relays the one input stream its hosting Wayland compositor already merged rather than driving hardware devices itself.
- **Wayland-native multi-pointer/multi-seat within one Mutter session** (a hypothetical Wayland equivalent of MPX). No such mechanism is documented as existing in Mutter regardless of RHEL version — Wayland's seat model is deliberately one-seat-per-session; genuine multi-seat on Wayland means genuinely separate sessions (B2), not one session with multiple attributable input sources.
- **GTK4/Wayland/`gnome-kiosk` CSS Motif theme, claimed as meeting requirement 2 in full.** Not ruled out as an implementation — it runs fine, and per Red Hat's own deprecation notice it's the *recommended* toolkit direction — but it does not meet requirement 2 as worded ("not just decoration"): window actions stay GNOME/Mutter-native regardless of theming, and (per §3) that's a platform ceiling, not a gap more theming work would close.
- **Live window-position syncing between two independent Mutter sessions (B2/B4/B5), via ordinary GTK4/Wayland client APIs.** Same root cause as the position-persistence gap already documented in `session_base_decision.md`: no client-facing API to read or set a toplevel's absolute screen position, on either end of the sync. Ruled out for the ordinary client-API approach specifically — not ruled out architecturally, since a matched pair of custom GNOME Shell extensions using Mutter's in-process `Meta.Window` API is a real, if expensive, way around it (§4, §5 Candidate 6). *(2026-10-08: an X11 client under Xwayland also gets around it — §3 A4.)*

**Reopened (2026-10-08) — previously treated as ruled out, shown here to be wrong:**
- **"No X11 window-management semantics on RHEL 10."** Implied throughout this document by the Xorg removal. Disproved on-box: Mutter honors ICCCM/EWMH and Motif hints for Xwayland clients (§3 A4). What stays ruled out is narrower: real `mwm` as the window manager and MPX, both of which genuinely need a standalone X server.

## §7 — Open items before committing engineering time to any candidate

- The Motif/Xorg availability findings in §"In short" came from Red Hat's public documentation and KB, not a live check on the actual RHEL10.1 box — cheap to confirm directly with `dnf search motif`, `dnf search mwm`, and `dnf search xorg-x11-server-Xorg` against the box's enabled repos before treating A3/B1 as permanently closed.
- **A4 (added 2026-10-08):** the X11-protocol behavior is verified (§3). Before committing to a GTK3 port, a small GTK3/X11 prototype (menu bar + radar + one child window) should confirm the two untested points — `DESKTOP` type for the radar background, and whether window sizes negotiate back to natural size on X11 the way they did on Wayland — and that GTK3's own API calls (`gtk_window_move()`, `gtk_window_set_keep_above()`, `gtk_window_set_type_hint()`) behave like the raw Xlib calls the test used.
- **B2's remaining open question (narrowed):** the mechanism itself is now confirmed as a current, fully-documented RHEL 10 procedure (Admin guide §1.5), not an inference — what's left is purely empirical: confirm two different accounts can complete GDM remote-login RDP connections *at the same instant*, via two concurrent `xfreerdp` sessions to two different accounts on the RHEL10.1 box, watched for whether the second hangs the way the mirror-mode VNC fanout did. This is a genuinely untested configuration, not a retest — the project's existing concurrent-RDP test (`rdp-input-attribution.md` §2) exercised the mirrored-session path, not remote-login mode; see the B2 table above for the exact distinction. Given the mechanism is GDM's own login screen (which has supported simultaneous multi-user logins locally for decades) exposed over RDP, this check is now closer to "confirm the obvious" than "resolve a real unknown," but it's still the cheapest possible thing to verify before building on top of it.
- **B4:** confirm `tigervnc-server` and the per-user `vncserver.users` multi-user pattern are still documented/packaged for RHEL 10 (found so far in RHEL 9's doc structure, which was reorganized for RHEL 10).
- **B5:** confirm local `systemd-logind` multi-seat actually works on RHEL 10 by testing it directly — don't treat the RHEL 7 documentation as suggestive either way. The full current RHEL 10 admin guide doesn't mention this feature at all, despite covering adjacent niche desktop-admin territory in detail, which is a real absence given the project's already-confirmed pattern of RHEL 9→10 dropping legacy desktop features (Xorg, Motif). A second physical seat (USB hub tagged via `udev` `ID_SEAT`, `loginctl seat-status`, confirming GDM actually spawns a second graphical greeter) is the only way to know.
- **Which product is actually wanted:** confirm whether requirement 3b's "including live window moves/resizes" is a hard requirement or can be relaxed (§4, §5). This is the single highest-leverage open item — it decides whether the cheap, well-documented B2/B4/B5 candidates are in play at all, or whether the project needs to commit to B3/B6 (speculative for co-located) or the dual-Shell-extension escalation (Candidate 6, most expensive option in this document).
- **Candidate 6's escalation:** if pursued, first resolve `session_base_decision.md`'s standing `gnome-kiosk` vs. `gnome-shell` question — this candidate only exists on the `gnome-shell` branch of that decision.
- The widget-level interaction work in A2 (Motif-authentic arm/disarm, drag thresholds, menu mnemonics via GTK4 gesture controllers) hasn't been scoped in detail — worth a small design pass on exactly which Motif behaviors matter most for the demo before committing engineering time, since "authentic Motif interaction" is a spectrum, not a single checkbox.
- Whether requirement 3's topologies (3a co-located, 3b physically separate monitors/locations) are both in scope now, or one is a later phase — determines whether to prioritize B5 (co-located) or B2/B4 (remote) first.

## §8 — Where this leaves the decision

> **Update (2026-10-08):** Axis B is dropped (single operator), and `gnome-kiosk` is no longer a target — the direction is a locked-down standard `gnome-shell` session. Within that, the live decision is now on Axis A: stay on GTK4/Wayland with the custom Shell extension doing window control over D-Bus (the current implementation), or port to **A4** (GTK3 on Xwayland), which gives the application direct, standard X11 control of its own windows and reduces the extension to session lockdown only. A4's mechanism is verified on RHEL 10.2; its remaining cost is the port and a forward-looking dependency on Xwayland. The text below is the 2026-07-10 analysis, kept as written.

No candidate here is being recommended as final — that's the point of this reset. Two things closed off since the first draft, for different reasons: the "leave Wayland behind entirely" branch (real `mwm`, MPX) is closed by Red Hat's own documentation of what RHEL 10 removed; and "isolated sessions kept in sync" (B2/B4/B5) turns out not to cover live window-drag mirroring at all, closed by the same client-API gap this project already found and documented for single-session position persistence.

That second finding is the one worth a decision before any more of this gets scoped, because it splits the whole document into two different products (§5): a cheaper one (B2/B4/B5) that matches requirement 3b's spirit but not its literal "including live moves" wording, and a more expensive one (B3's coarse variant, or the dual-Shell-extension path, Candidate 6) that satisfies more of the literal wording but costs custom protocol code or a second standing architecture decision. B6 — the one candidate that looked like it might satisfy the literal wording *without* that cost — turned out to share B0's root flaw once examined closely (§4) and has been retracted; it isn't a live option. **Recommended next step: settle which of those two products the demo actually needs before scoping engineering work on either** — it's a cheap question to ask and an expensive one to get wrong in either direction. Since the last revision, B2's own footing got considerably firmer: its full procedure is now confirmed as current, official RHEL 10 documentation (not inferred from older RHEL 9 docs), so if the "spirit not literal wording" branch is acceptable, B2 is close to ready to build rather than needing a package/availability check first — only the simultaneous-concurrency test in §7 remains. B4 still needs its own RHEL 10 confirmation; B5 specifically should be treated as an **untested hypothesis carried over from EOL RHEL 7 documentation**, not a likely-to-work fallback, given the same guide that documents everything else about RHEL 10 desktop administration in detail says nothing about it.
